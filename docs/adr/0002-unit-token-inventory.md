# ADR 0002: Unit-token holds and relational uniqueness guard

- **Status:** Accepted
- **Context:** A hot inventory counter/row is a contention point and a non-atomic read-modify-write can oversell. A Redis Cluster script cannot atomically touch keys in different hash slots. A single per-item claim key would also funnel all hold claims for a hot item into one cluster slot.
- **Decision:** Represent each unit as a token. For a specific seat, route to `hash(unit_id) % S`; for an any-unit request, start at `hash(user_id) % S` and probe/walk shards deterministically until a candidate shard is found. Before reserve, atomically bind the request to one shard using a per-hold Redis key `hold-claim:{base64url(hold_id)}` and `HSETNX`. The key's hash tag is derived from the opaque hold ID, not the item ID, so claims distribute across Redis Cluster slots. The claim stores `hold_id`, `item_id`, `user_id`, `requested_unit_id` (empty for any-unit) and selected shard. Mismatched replays are rejected. Claim creation and inventory reserve are separate operations because their keys are in different slots. The reserve Lua script uses only keys in the selected inventory shard's `{item:shard}` hash slot and atomically transitions one available unit to a TTL `HELD` record, writes the deadline and appends a same-slot outbox event. Checkout moves `HELD → PAYING`; the reaper returns only expired `HELD` units.
- **Claim-drain rule:** Once a claim is created, it never moves. If a selected any-unit shard drains after the stock probe but before the atomic reserve script, reserve returns `SOLD_OUT` for that hold ID. Do not retry another shard with the same hold ID; a rare false sold-out is preferred to a possible second allocation after an ambiguous response. A retry first reads the claim and always targets the exact same shard. Retain the claim/tombstone for at least the full hold, order and idempotency-replay lifetime; never expire it while the hold or payment can still be retried.
- **Redis Cluster implementation contract:** Encode the hold ID as base64url inside the hash tag (for example `hold-claim:{<base64url-hold-id>}`) so caller-supplied braces cannot alter slot selection. `HSETNX` creates the immutable claim field/value. Each inventory script receives only keys with the selected `{item:shard}` tag; no script attempts to atomically access the claim key and inventory keys across slots.
- **Final guard:** PostgreSQL partial unique index on live `(item_id, unit_id)` ownership. A conflict persists the loser as `CANCELLED` with payment `NOT_ATTEMPTED` and `inventory_disposition=FORFEIT`, then forfeits the `PAYING` hold using `ForfeitProofNotAttempted`; this proof is valid because the unique guard short-circuits before any PSP call. A `PAYING` hold with `AUTHORIZED` or `UNKNOWN` payment cannot be forfeited until the PSP outcome is definitively voided/declined. The unit is never returned to availability by the Forfeit operation.
- **Alternatives:** DB row lock only; optimistic counter; per-seat distributed lock; cross-slot Lua transaction (not supported by Redis Cluster); mutable claim that walks again after a reserve error.
- **Consequences:** Redis state must be rebuildable and retries must retain the same shard claim. A crash after claim but before reserve, or a shard draining between probe and reserve, can cause temporary false sold-out for that hold ID, but cannot allocate a second shard. `MemoryClaimRepository` in the current Go slice is a local test stand-in; production must use the Redis per-hold `HSETNX` contract.


## One-way hold-ID lifecycle and terminal TTL

The per-shard hold record is a stateful tombstone. `reserve.lua` checks `prior.state` before replay: `RELEASED` returns terminal `ErrHoldReleased`; `FORFEITED` returns terminal `ErrHoldForfeited`; neither returns `OK` or allocates. `HELD`/`PAYING` return the same active hold; `CONFIRMED` returns the same confirmed hold without allocating; unknown states fail closed. `release.lua`, `confirm.lua` and `forfeit.lua` retain terminal records and never delete them on the hot path. `forfeit.lua` is a permanent quarantine operation, not the ordinary payment-decline path (use `release.lua` for a normal definitive decline/void). It requires a trusted `ForfeitProof` derived from the durable payment row in a fenced transaction. `HELD` accepts only `NOT_ATTEMPTED`. `PAYING` accepts `NOT_ATTEMPTED` only for a persisted unique-index loser that short-circuited before PSP, or `PSP_DECLINED`/`PSP_VOIDED` after a definitive result is durably recorded. `AUTHORIZED`, `UNKNOWN`, missing proof and ambiguous outcomes are rejected; resolve/void them before forfeiture. A definitive decline/void proof permits forfeiture only where a separate safety/integrity decision requires permanent quarantine; it does not mean ordinary declines should forfeit rather than release. The Lua proof is a caller assertion, not independent PSP verification. An already-`FORFEITED` record is an idempotent no-op without fresh proof. Forfeiture is idempotent for `FORFEITED`, rejects `RELEASED`/`CONFIRMED`, removes the deadline and appends `HoldForfeited` without touching the available set.

The per-hold `hold-claim:{base64url(hold_id)}` has no TTL while `HELD` or `PAYING`. After a terminal `RELEASED`, `CONFIRMED` or `FORFEITED` transition is committed in the shard slot, the Go repository may apply `EXPIRE` to the separate claim key using a configured retention longer than the maximum admission-token validity, client retry, relay/consumer redelivery, PSP idempotency, webhook and regional-recovery replay windows. The shard-side terminal tombstone (`RELEASED`, `CONFIRMED` or `FORFEITED`) is retained at least as long as the claim TTL plus a safety margin; expired admission credentials are rejected before reserve. If the cross-slot EXPIRE call fails, retain the claim (safe leak) and alert; never delete the terminal shard record early. Cleanup runs only after all replay horizons are closed.
