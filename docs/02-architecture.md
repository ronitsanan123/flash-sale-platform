# 2. Proposed Architecture

## Design summary

Shape demand before it reaches stateful services. The edge waiting room serves queue polling from a cached admission watermark and issues short-lived signed admission tokens. A stateless gateway verifies tokens offline and applies priority-aware rate limiting. An inventory service atomically moves one concrete unit token into a time-bounded hold. Checkout locks a hold into `PAYING` and returns `202 Accepted`; an asynchronous event pipeline creates the order/payment intent, authorizes through the PSP, confirms inventory only after definitive authorization and the required cross-region durability acknowledgement, and performs deferred capture.

Redis is the fast inventory/hold coordinator, not the only oversell defence. PostgreSQL owns durable orders/payments, durable idempotency and the unique live-owner constraint. A Kafka-compatible log distributes ordered order events. A key-value store serves order-status and catalog read models. Analytics consumes the event stream asynchronously. The AWS reference mapping uses self-managed PostgreSQL 16 on EC2 with a configured remote synchronous standby; Aurora Global Database is not used for the RPO 0 confirmed-order path.

## Request flow

1. **Browse and availability.** Browse/catalog/availability reads use the CDN cache and absorb the approximate 50:1 read/write mix. Availability is bucketed (`many`, `few`, `sold out`) and may be stale for one second plus a bounded stale-while-revalidate window. Cached counts never allocate inventory.
2. **Join and poll.** Queue join and polling enter the WAF and virtual waiting room. At a 20-second jittered poll interval, 10M waiting users imply about 500K edge queue polls/s (planning assumption), not origin requests. Queue tokens are signed; pre-drop arrivals can be randomized once, later arrivals are FIFO. Polling is jittered and answered from the cached watermark rather than making one origin call per poll.
3. **Publish the admission watermark.** The admission controller publishes a conservative stock- and PSP-aware watermark every second using a dedicated HA control-plane keyspace/partition, separate from hot inventory shard keys. It emits `OPEN` when reservable units exist, `TEMPORARILY_UNAVAILABLE` when availability is zero but `HELD` / `PAYING` units may return, and terminal `SOLD_OUT` only when no available or recoverable units remain. The terminal sold-out state gives all remaining waiting users a final answer. Inventory publishes aggregate stock summaries to control state; workers publish PSP breaker/effective authorization capacity. If control state is unavailable, the edge holds the last watermark and fails closed for new admission; CDN browse remains available.
4. **Issue an admission token.** The waiting room returns a short-lived signed token only for admitted users. The gateway validates signature, issuer/audience, expiry, item scope and unique token ID offline.
5. **Route admitted requests.** Reserve and checkout writes require a valid admission token. Order-status reads use separate customer/order authorization and do not depend on admission-token expiry. PSP webhooks use a separately authenticated route and bypass the waiting room.
6. **Reserve inventory.** The router uses `hash(unit_id) % S` for a specific seat. For an any-unit request it starts at `hash(user_id) % S` and probes/walks shards deterministically until a stock candidate is found. Before reservation, an immutable claim bound to item/user/requested unit is created with `HSETNX` under a per-hold Redis key `hold-claim:{base64url(hold_id)}`; claim keys therefore distribute by hold ID instead of creating one hot per-item claim slot. Mismatched replays are rejected. Claim placement is separate from the per-shard reserve script because the keys occupy different Redis Cluster slots. The reserve Lua script uses only keys in the selected inventory shard's hash slot and atomically creates the `HELD` hold, deadline and outbox event. If the bound shard drains between probe and reserve, return `SOLD_OUT` for that hold ID and do not remap it; a rare false sold-out is safer than a second allocation.
7. **Accept checkout.** Checkout compare-and-sets `HELD → PAYING` before acknowledging `202 Accepted` and a status URL. The reaper releases expired `HELD` holds only. It re-scores overdue `PAYING` holds and appends `HoldPayOverdue` to the outbox; timer expiry is not proof that payment failed.
8. **Relay the outbox.** Redis Stream relay publishes checkout events to Redpanda. It acknowledges a stream entry only after broker acknowledgement; pending entries are replayed after restart.
9. **Publish to the event log.** The Kafka-compatible log has 12 partitions keyed by `order_id`, preserving per-order ordering. Delivery is at least once.
10. **Consume checkout.** Workers process each partition sequentially with bounded retries, requeue with an attempt counter, then route unresolved events to the DLQ and mark their order outcome `UNKNOWN` for reconciliation. Commit the Kafka offset only after durable successful handling, durable retry/requeue publication, or durable DLQ publication plus the corresponding `UNKNOWN` state. The reconciler monitors and triages the DLQ; replay is controlled and audited after remediation, never blind.
11. **Create durable order intent.** Before calling the PSP, a worker transaction creates order `PENDING_PAYMENT` and payment `INTENT`. PostgreSQL owns durable idempotency and enforces the partial unique index on `(item_id, unit_id)` for live orders. The PSP call is permitted only after this transaction succeeds. A unique-index loser is persisted as `CANCELLED`, bypasses PSP authorization and confirmation (steps 12-13), short-circuits to step 14, and forfeits its unit pending reconciliation. The worker projects this committed `PENDING_PAYMENT` state to KV with a monotonic status version.
12. **Authorize payment.** Only an order whose step-11 intent transaction succeeded reaches PSP authorization. The worker uses `Idempotency-Key: order_id`; the initial authorization allocation is at most 1,400 calls/s (assumption). A timeout is `UNKNOWN`, not decline: query/retry the same key. If an attempt must be abandoned, void by key before cancellation/release, subject to the PSP's documented idempotency/tombstone semantics. PSP calls and DB writes carry the current fencing epoch.
13. **Commit confirmed state.** On definitive authorization, the worker compare-and-sets payment to `AUTHORIZED` and order to `CONFIRMED`. PostgreSQL uses synchronous primary/standby replication to one remote standby with `synchronous_commit=on`; the primary commit waits for the remote standby to flush commit WAL to durable storage. This is primary + one remote standby (2-of-2), not a majority consensus quorum. Customer-visible confirmation and its KV projection are released only after the primary commit returns with the remote WAL-flush acknowledgement. If the standby/WAN is unavailable, confirmation commits pause.
14. **Finalize inventory.** Only after remote standby WAL-flush acknowledgement has allowed the PostgreSQL commit to return does the worker mark the Redis unit sold; it is never re-offered. On definitive decline/void, the worker records `CANCELLED` and releases the hold safely. A PostgreSQL uniqueness-guard loser arrives here through the step-11 short-circuit, never calls PSP, and has its hold/unit forfeited pending reconciliation. A failed KV projection is rebuilt from PostgreSQL.
15. **Read status immediately and safely.** The API uses KV as the fast path. On a KV miss or projection lag it reads authoritative PostgreSQL state. If the worker has not created the order row yet (the short window immediately after `202`), it resolves the hold from Redis and returns `PAYING` / `PROCESSING`, not a false `404`. Status versions are monotonic so delayed projections cannot regress a later state.

## Supporting and recovery flows

- **Closed-loop backpressure:** Order workers publish PSP breaker-open state and effective authorization capacity into a dedicated replicated HA control-plane keyspace/partition, separate from the per-item inventory shard keys. Inventory publishes aggregate stock summaries into control state; ADM reads stock summary and PSP state without depending on one hot inventory shard. Loss of an inventory shard must not blind admission; loss of the dedicated control plane freezes the last edge watermark and fails closed for new admissions. Existing `PAYING` holds continue through query/retry/void resolution; they are not released by the admission pause.
- **Deferred capture:** The capture sweeper reads `CONFIRMED` + `AUTHORIZED` orders pending capture. It performs idempotent capture off the order-worker hot path, using a token bucket for every PSP call. It compare-and-sets `CAPTURED` in PostgreSQL and only after that DB commit publishes the next monotonic KV payment-status version.
- **Status projection timing:** `PENDING_PAYMENT` is projected after the order-intent transaction commits; `CONFIRMED` only after the PostgreSQL primary commit returns following remote standby WAL flush; `CANCELLED` after a definitive decline/void transaction; and `CAPTURED` after the capture transaction commits. Writes carry a monotonic per-order version and are conditional on the stored version being lower. A KV miss/lag falls back to PostgreSQL; if no order row exists yet immediately after `202`, Redis hold state returns `PAYING` / `PROCESSING`.
- **PSP webhooks:** Async authorization, capture and 3DS outcomes enter through authenticated webhook ingress, which verifies signature/timestamp and deduplicates event IDs before appending events to the log. Polling by the same idempotency key remains the fallback for missing/late callbacks. The production architecture supports webhooks; the prototype may implement polling first.
- **DLQ and reconciliation:** Events that exhaust bounded retries enter the DLQ. The reconciler monitors and triages them; replay is operator-approved, audited and performed only after remediation. Reconciliation compares Redis, PostgreSQL and the PSP ledger, detects duplicate ownership, orphan authorizations, stuck `PAYING` holds and unit-conservation drift. Automated fixes touch only records older than a safety threshold and in terminally safe states.
- **Analytics:** Analytics consumes lifecycle events asynchronously and has no dependency in the checkout path.
- **Multi-AZ failover:** Gateway, reservation and webhook ingress replicas run statelessly in both AZs. Admission is leased per item, relays per Redis stream, reapers per shard, workers per Kafka partition, capture tasks per payment/task and reconciliation per job. A takeover requires a higher fencing epoch; no worker role is pinned to AZ a.
- **Multi-region:** One home region is the single writer for an item. Other regions serve edge/waiting-room and read traffic; all writes are forwarded to the home-region gateway with a fencing epoch. The separate standby region hosts a PostgreSQL synchronous standby. The primary + one remote standby are both required (2-of-2); this is not a majority consensus quorum. `synchronous_commit=on` waits for remote WAL flush. If the WAN/standby is unavailable, confirmation commits pause. Event-log replication may be asynchronous, but failover requires fencing, WAL recovery and reconciliation before admissions reopen.
- **Observability:** Critical services export metrics, traces and structured logs to OpenTelemetry/Prometheus. Telemetry is non-critical and never gates reserve, checkout or payment resolution.

## Inventory and hot-key strategy

Inventory consists of concrete unit tokens rather than a single mutable stock counter. In Redis Cluster, every key passed to one Lua script must share a hash slot. For a specific seat, the target shard is `hash(unit_id) % S`; for an any-unit request, the router starts at `hash(user_id) % S` and walks shards deterministically. A separate immutable `HSETNX` claim binds `hold_id` to the selected shard before the reserve script runs. If the client times out, every retry resolves the same claim and shard. A claim may remain without a hold after a crash, causing temporary false sold-out for that hold ID, but cannot allocate a second shard. The per-shard reserve script atomically moves the unit to `HELD`, records the expiry and appends the outbox event using same-slot keys.

PostgreSQL remains the final guard: `UNIQUE (item_id, unit_id) WHERE status <> 'CANCELLED'`. If this guard trips, the loser is recorded as cancelled in a separate transaction and its hold is forfeited/marked unavailable rather than returned to sale until reconciliation proves it safe.

## Hold states

`HELD → PAYING → CONFIRMED`, `RELEASED` or `FORFEITED`; an expired `HELD` hold can also move directly to `RELEASED`. `RELEASED`, `CONFIRMED` and `FORFEITED` are terminal tombstones for the hold ID. `Release` returns the unit to availability only for an expired `HELD` hold or after a definitive PSP decline/void for `PAYING`. `Forfeit` is used for a PostgreSQL unique-guard loser: `HELD` requires durable `NOT_ATTEMPTED`; `PAYING` requires either durable `NOT_ATTEMPTED` for a unique-guard loser that never called PSP, or a definitive persisted PSP `DECLINED`/`VOIDED` result. `AUTHORIZED`, `UNKNOWN` and ambiguous outcomes are rejected until resolved/voided. The caller derives this proof from the durable payment state in a fenced transaction; Redis does not independently verify the PSP. Ordinary definitive decline/void uses `Release`; Forfeit is reserved for permanent quarantine when a separate integrity decision requires it. Forfeit removes the deadline, records `FORFEITED`, emits `HoldForfeited`, and never returns the unit to availability. An already-`FORFEITED` replay is an idempotent no-op. Repeated `Forfeit` is idempotent; reserve replay of `RELEASED` returns `ErrHoldReleased`, and replay of `FORFEITED` returns `ErrHoldForfeited`, never allocating a second unit. The reaper releases expired `HELD` holds but repeatedly re-scores overdue `PAYING` holds as `HoldPayOverdue`. Redis server time is used for deadlines. A timer is never evidence that a payment failed. Terminal claim/tombstone retention spans every accepted credential and replay horizon; `HELD`/`PAYING` claims never expire.

## Failure direction

Network failures, timeouts and ambiguous payment outcomes prefer temporary under-selling through stranded or `PAYING` holds; they never justify an unsafe release. A unique PostgreSQL guard loser is different: its hold is explicitly `FORFEITED` and its unit remains unavailable under that hold. Forfeit does not return inventory to sale; any later re-offer requires authoritative reconciliation proving a separate safe disposition.

## Data placement

| Component | Data | Reason |
|---|---|---|
| CDN / edge | static assets, catalog cache, coarse availability, queue watermark | absorbs massive read/poll volume |
| Redis inventory / MemoryDB | unit tokens, holds, deadlines, per-shard outbox streams | low-latency atomic inventory coordination; inventory shard keys remain separate |
| Dedicated HA control-plane store/keyspace | per-item watermark, three-state stock summary, PSP breaker/effective authorization capacity | replicated/failover-isolated admission state; one inventory shard loss cannot blind the waiting room |
| PostgreSQL 16 on EC2 (AWS reference) | orders, payments, durable idempotency, `region_leases`, fencing epochs, inventory disposition, unit ownership constraints and standby-durable PSP scan checkpoints; synchronous remote standby | transactional source of durable ownership, writer fencing and deduplication; named remote synchronous standby waits for WAL flush |
| Redpanda / Kafka | ordered lifecycle events keyed by `order_id`, DLQ | decouples workers and supports replay/triage |
| DynamoDB / KV | order-status read model, catalog documents | scalable reads without DB connection pressure; not payment authority |
| Columnar analytics | event-derived aggregates | isolates analytical load |
| PSP | authorization/capture/void ledger | external payment truth |

### PostgreSQL reference deployment

The RPO 0 confirmation path requires PostgreSQL synchronous primary/standby replication to a remote-region standby. Configure a named synchronous standby via `synchronous_standby_names` and `synchronous_commit=on` so the primary waits for remote WAL flush before returning commit success. For the AWS reference mapping, use self-managed PostgreSQL on EC2 (or a specifically validated PostgreSQL service with this exact cross-region synchronous-commit behaviour). Do not map this guarantee to Aurora Global Database: its cross-region replication is asynchronous. If the remote standby is unavailable, confirmation commits pause.

## Caching

- CDN: catalog/static for minutes; availability for about one second with stale-while-revalidate; queue watermark for one second.
- Service-local: one-second availability cache with singleflight/coalescing.
- Redis: authoritative reservation path only; do not use cached availability as an allocation decision.
- Status: KV is a versioned projection of every committed order/payment transition (including `PENDING_PAYMENT`, `CONFIRMED`, `CANCELLED` and `CAPTURED`); PostgreSQL remains authoritative. On KV miss or lag, status reads fall back to PostgreSQL and, before the order row exists, Redis hold state (`PAYING` / `PROCESSING`). A stale projection must never create a false confirmation or regress a newer status version.

## Multi-AZ and worker ownership

The home region uses two availability zones (AZ a and AZ b). Both contain app and worker replicas; no third home-region AZ is assumed. A separate standby region hosts the synchronous PostgreSQL standby used for acknowledged confirmation durability.

Gateway, reservation and webhook ingress replicas run statelessly in both AZs. Admission control, relay, reaper, order worker, capture sweeper and reconciler are deployed in both AZs. Order workers publish PSP breaker/effective authorization capacity to a dedicated replicated HA control-plane keyspace/partition; inventory publishes aggregate stock summaries there separately from its hot shard keys. Admission reads this control state and reduces/pauses watermark advancement when payment capacity degrades. Loss of an inventory shard or an incomplete/stale stock summary is treated conservatively and must not make the controller infer `OPEN` or terminal `SOLD_OUT`; loss of the dedicated control plane freezes the last edge watermark and fails closed. Ownership is not pinned to AZ a: admission is leased per item, relays per Redis stream, reapers per shard, consumers per Kafka partition, and periodic jobs use leases/fencing. A leader-elected regional `lease-manager` renews the logical writer lease independently of order-worker loops; a renewal with zero updated rows or missed safety deadline self-fences and pauses admissions/confirmation. After an AZ loss, surviving replicas acquire role ownership with a higher fencing epoch before acting; replacing a worker pod alone does not change `region_leases.owner_id`.

## Scale and warm capacity

Scheduled drops: pre-warm gateway, reservation workers, connection pools, broker partitions, Redis capacity, caches and network limits at T-30 minutes. Unscheduled drops: keep the edge queue armed and engage it based on ingress RPS, in-flight concurrency, latency and errors in under ten seconds. Autoscale on leading signals such as RPS per pod, in-flight requests and log-lag age; CPU alone trails a 30-second ramp.

## Multi-region model

One home region is the single writer for an item. Other regions serve edge, waiting-room and read traffic, but all writes are forwarded to the home-region gateway with a fencing epoch. Stale/missing remote standby ACK pauses confirmation and new admissions. The `region_leases` row is renewed by one leader-elected lease-manager per home-region writer lease; `owner_id` is a logical region/cluster writer identity shared by replicas, never a worker pod hostname. The per-region lease row is not a global fence if a network partition leaves two independently writable regional primaries. Promotion is allowed only after the old primary is confirmed unreachable or infrastructure-fenced; dual-primary split-brain protection requires external/consensus fencing and is outside the current prototype. Customer-visible confirmation waits for a PostgreSQL remote standby WAL-flush acknowledgement (`synchronous_commit=on`). Primary + one remote standby are both required (2-of-2, not a majority quorum); this provides RPO 0 for acknowledged confirmations but pauses confirmation commits when the WAN/standby is unavailable. Event-log replication may remain asynchronous only if missing events can be rebuilt from durable database/outbox state before failover is reopened.

## Webhook and observability paths

PSP webhooks are accepted on a separate authenticated route with signature verification, timestamp/replay checks and event-ID deduplication. They bypass the waiting room and are converted to log events; polling by idempotency key remains the fallback. OpenTelemetry traces, structured logs and Prometheus metrics are emitted by edge-facing services, workers and data clients to a non-critical telemetry plane. Telemetry loss must not block the sale path.


## PSP void capability and prototype boundary

The mock PSP is specified to tombstone an idempotency key after a definitive void and to reject any late/retried authorization for that key. A production PSP must be evaluated for this exact guarantee. If it cannot guarantee void-by-key tombstoning, keep unresolved `UNKNOWN` authorizations in `PAYING`; do not release on timeout or idempotency-window expiry alone. Release only after a definitive provider outcome or a provider-guaranteed authorization-finality boundary. The local single-PostgreSQL Compose profile uses an explicit `StandbyAckGate` backed by isolated control-plane Redis to simulate fail-closed application behaviour; this is not proof of real remote PostgreSQL WAL-flush replication.
