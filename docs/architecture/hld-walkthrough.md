# HLD Walkthrough

The shaded subgraphs show deployment, failure and ownership scopes; they do not mean every component nested under a parent fails as one indivisible unit. AZ a and AZ b are independent home-region failure domains. The data tier is a multi-AZ service boundary; remote edge/read regions, the standby database region, the external PSP and non-critical observability are separate dependency boundaries. APP and WORKER boxes inside each AZ are logical deployment tiers, not separate failure domains. Application replicas run in both AZs. Worker replicas also run in both AZs; leases, Kafka partition ownership and fencing determine active ownership and allow takeover after an AZ failure. The primary numbered card layout is serpentine: row 1 reads left-to-right (1-5), row 2 right-to-left (6-10), and row 3 left-to-right (11-15).

## Numbered customer and order flow

1. **Browse and availability.** Browsers and mobile apps use the CDN for static assets, catalog and coarse availability. This read path absorbs the approximate 50:1 read/write mix. Availability may be one second stale plus bounded stale-while-revalidate; it is never used to allocate inventory.
2. **Join and poll.** Queue join and polling enter the WAF and virtual waiting room. With 10M waiting users and a 20-second jittered poll interval, the edge handles approximately 500K queue polls/s (planning assumption); polls are answered from a cached admission watermark and signed queue state rather than one origin call per poll.
3. **Publish admission watermark and confirmation gate.** The admission controller holds a per-item lease and publishes a stock- and PSP-aware watermark every second through a dedicated highly available control-plane keyspace/partition, replicated and isolated from the hot inventory shard keys. It publishes three inventory states: `OPEN` when reservable units exist; `TEMPORARILY_UNAVAILABLE` when available is zero but `HELD` / `PAYING` units may still return; and terminal `SOLD_OUT` only when no available or recoverable units remain. Separately, it publishes an admission gate (`ACTIVE` or `PAUSED`): a stale/missing remote-standby WAL-ACK health signal, PSP breaker/capacity failure, unknown stock, or lost control plane pauses issuance of new admission tokens. Standby-ACK loss is `PAUSED` / temporarily unavailable, never terminal `SOLD_OUT`. The waiting room continues to serve queue status and preserves users' place; browse remains available from CDN. If the control plane itself is unavailable, the edge holds the last watermark and fails closed for new admissions.
4. **Issue admission token.** The waiting room issues a signed, short-lived token only to admitted users. The gateway verifies signature, issuer/audience, expiry, item scope and unique token ID offline.
5. **Route admitted requests.** Reserve and checkout writes require a valid admission token. Order-status reads use separate customer/order authorization, so status access does not expire with the admission token. PSP webhooks use a separately authenticated route and bypass the waiting room.
6. **Reserve inventory.** The reservation router chooses the shard deterministically: a specific seat uses `hash(unit_id) % S`; an any-unit request starts at `hash(user_id) % S` and probes/walks shards deterministically until a candidate is selected. Before reservation, it creates an immutable claim with `HSETNX` under the exact per-hold Redis key `hold-claim:{base64url(hold_id)}`; the encoded hold ID is the Redis Cluster hash tag, not a shared per-item key. The claim binds `hold_id`, `item_id`, `user_id`, requested `unit_id` (empty for any-unit) and selected shard. Every retry first reads this claim and targets that exact shard; mismatched replays are rejected. Claim placement is separate from the per-shard reserve script because the claim and inventory keys occupy different Redis Cluster slots. The reserve Lua script uses only keys in the selected shard's hash slot and atomically moves one unit to `HELD`, records its deadline and appends the outbox event. If the bound shard drains after the stock probe but before reserve, return `SOLD_OUT` for that hold ID; do not walk or remap the same hold ID to another shard, even if another shard has stock. Retain the claim/tombstone for the full hold, order and payment-replay lifetime. This accepts a rare false sold-out rather than risking a second allocation after an ambiguous response.
7. **Accept checkout.** Checkout compare-and-sets `HELD → PAYING` and returns `202 Accepted` plus a status URL. The reaper releases only expired `HELD` holds. An overdue `PAYING` hold is re-scored and a `HoldPayOverdue` event is appended to the outbox; a timer never releases a `PAYING` hold.
8. **Read Redis outbox.** The relay has one active lease owner per Redis stream. It publishes stream entries to the Kafka-compatible log and acknowledges the Redis entry only after broker acknowledgement. Pending entries are replayed after relay restart.
9. **Publish event.** Events are produced to the log; the relay's acknowledgement follows the broker acknowledgement.
10. **Consume checkout.** The log has 12 partitions keyed by `order_id`. Workers process each partition sequentially. They use bounded in-place retries, requeue with an attempt counter, and then route unresolved events to the DLQ with an `UNKNOWN` outcome for reconciliation. Commit the consumer offset only after durable successful handling, durable retry/requeue publication, or durable DLQ publication plus the corresponding `UNKNOWN` state. The reconciler monitors and triages the DLQ; replay is audited and only follows remediation, never blind automatic replay.
11. **Create locally durable order intent.** Before calling the PSP, a worker transaction creates an order in `PENDING_PAYMENT` and a payment intent in `INTENT`. This transaction uses `synchronous_commit=local`: its WAL is flushed locally, but this intermediate intent is not yet durable in the remote standby and is not customer-visible `CONFIRMED`. PostgreSQL owns durable order/payment idempotency in the home region, and the partial unique index on `(item_id, unit_id)` remains the final live-unit ownership guard. The PSP authorization call is conditional on this transaction succeeding. A unique-index loser is persisted as `CANCELLED`, its unit is forfeited pending reconciliation, and it short-circuits directly to step 14; it NEVER calls the PSP. After the successful local intent commit, the worker projects `PENDING_PAYMENT` to KV with a monotonic status version. Projection failure does not roll back the order; status reads fall back to PostgreSQL.
12. **Authorize payment.** Only an order whose step-11 intent transaction succeeded reaches the PSP. The worker authorizes with `Idempotency-Key: order_id`, using an assumed authorization allocation of at most 1,400 calls/s from the PSP quota. The PSP request metadata includes `order_id` (also the idempotency key), `item_id`, `unit_id`, `user_id`, home-region identity and fencing epoch. The PSP contract must support both (a) lookup by idempotency key when the key is already known and (b) paginated discovery of authorization-ledger entries over a bounded time window when the order ID is unknown. Discovery pages must return the idempotency key/order ID, event and charge IDs, status, event time and retained metadata, plus a stable snapshot/cursor and a provider completeness watermark. The provider must retain searchable ledger data for at least the maximum regional recovery window. Contract-test discovery, pagination, metadata retention and completeness before production reliance. A normal single-order timeout remains `UNKNOWN`, not decline: query/retry the same known key. If the attempt must be abandoned, void by key before cancellation/release, subject to the PSP's documented idempotency/tombstone semantics. Only a definitive decline or confirmed void permits cancellation and hold release. PSP calls and DB writes carry the current fencing epoch.
13. **Commit confirmed state and handle the pre-ACK region-loss window.** After definitive PSP authorization, the worker compare-and-sets payment to `AUTHORIZED` and order to `CONFIRMED` in a transaction using `synchronous_commit=on`; with the named remote synchronous standby configured, the primary waits for the remote standby to flush the commit WAL to durable storage. This is two-location primary/standby durability (primary + one remote standby, both required), not a majority consensus quorum. Customer-visible `CONFIRMED` is exposed and projected to KV only after that commit returns. If the standby/WAN is unavailable, confirmation commits pause and the admission controller pauses new admission-token issuance when the standby-ACK health signal is stale or unavailable. If the home region is lost after PSP authorization but before the remote WAL-flush ACK, step-11's local-only intent and its `order_id` may both be absent from the promoted standby; recovery must not assume that it knows the idempotency keys. First fence the old writer and establish a higher fencing epoch. Then scan the PSP authorization ledger over a bounded time window beginning at the last standby-durable `complete_through` checkpoint (with an overlap) and ending after the failover cutoff plus the PSP's authorization-settlement grace. The scan is paginated against a stable snapshot and returns idempotency key/order ID, event/charge IDs, status, event time and metadata; REC filters entries by `home_region` and fencing epoch. Deduplicate overlapping pages/windows by PSP event ID and idempotency key. Require the PSP `complete_through` watermark to cover the scan end before treating discovery as complete. For every discovered or standby-known order ID, perform an individual key lookup and inspect surviving standby state for a durable step-13 `CONFIRMED` commit. Reconstruct idempotent recovery records for discovered attempts. Preserve only records with proof of the durable remote confirmation; void every authorization without that proof. Reconcile unit ownership, DB state and the PSP ledger, persist the new scan checkpoint durably, and reopen admissions only after the scan is complete and reconciliation finishes. If the PSP cannot provide complete ledger discovery and metadata retention, autonomous regional write failover is not safe: keep admissions paused until an independently cross-region-durable pre-PSP attempt journal or an equivalent recovery mechanism is available. No pre-ACK authorization or recovery record is represented as `CONFIRMED`.
14. **Finalize inventory.** Only after the remote standby WAL-flush acknowledgement has allowed the PostgreSQL commit to return does the worker mark the Redis unit sold; it is never re-offered. On a definitive decline/void, the worker instead records `CANCELLED` and releases the hold safely. A PostgreSQL uniqueness-guard loser arrives here by the step-11 short-circuit, never calls the PSP, and has its hold/unit forfeited pending reconciliation. KV is a read model, never payment authority.
15. **Read order status immediately and safely.** The API uses KV as the fast path. On a KV miss or projection lag it reads authoritative PostgreSQL state. If the asynchronous worker has not created the order row yet (the normal short window immediately after `202`), it resolves the hold from Redis and returns `PAYING` / `PROCESSING`, rather than a false `404`. The status endpoint does not require a live admission token. Status versions are monotonic and writes are conditional on version, so a delayed projection cannot regress a later state.

## Background, recovery and control-plane flows

- **Deferred capture:** The capture sweeper reads orders/payments that are `CONFIRMED` + `AUTHORIZED` and still pending capture. It performs idempotent capture off the order-worker hot path, using a token bucket for every PSP call. It compare-and-sets `CAPTURED` in PostgreSQL and only after that DB commit publishes the next monotonic KV payment-status version. Authorization/confirmation and capture are deliberately separate states.
- **Status projection timing:** `PENDING_PAYMENT` is projected after the order-intent transaction commits; `CONFIRMED` is projected only after the PostgreSQL primary commit returns following remote standby WAL flush; `CANCELLED` is projected after a definitive decline/void transaction; and `CAPTURED` is projected after the capture transaction commits. Every write carries a monotonic per-order version and is conditional on the stored version being lower. If KV is missing or behind, the API falls back to PostgreSQL; if no order row exists yet after `202`, it returns `PAYING` / `PROCESSING` from Redis hold state.
- **Closed-loop backpressure:** Order workers publish PSP breaker-open state/effective authorization capacity, and the database/replication monitor publishes remote-standby WAL-ACK health with a freshness timestamp, into a dedicated HA Redis/MemoryDB control-plane keyspace/partition, separate from inventory shard keys and replicated with lease/failover. A missing or stale standby-ACK heartbeat is treated as unavailable. Inventory publishes versioned aggregate stock summaries into control state; a missing/stale shard summary is treated as unknown and fails closed rather than being inferred as `OPEN` or terminal `SOLD_OUT`. Admission never relies on a single hot inventory shard for its watermark. The admission controller pauses new admission-token issuance (without changing inventory state to terminal `SOLD_OUT`) when the standby ACK is unavailable, the breaker opens, stock is temporarily unavailable, PSP capacity falls, or the control plane itself is unavailable. The waiting room preserves queue positions and continues status polling. Existing `PAYING` holds remain locked; the reaper emits `HoldPayOverdue` through the Redis outbox to Kafka and workers/reconciler, and never releases `PAYING` based on a timer.
- **PSP ledger checkpoint maintenance:** REC periodically scans the authorization ledger from the previous provider `complete_through` watermark minus an overlap, reads a stable paginated snapshot, folds events idempotently, reconciles changed attempts, and commits the new checkpoint with synchronous remote-standby durability. The checkpoint records home region, snapshot ID, scan bounds, provider watermark and fencing epoch. It advances only after every page and associated reconciliation complete; an interrupted scan leaves the prior checkpoint intact for safe replay.
- **PSP ledger discovery for regional recovery:** Per-key lookup is used only when the order/idempotency key is known (normal timeout and webhook resolution). If a home-region loss can also erase the locally committed intent and therefore the key, REC uses a stable paginated authorization-ledger scan over a bounded time window. The PSP must return the idempotency key/order ID, event/charge IDs, status, event time and `item_id` / `unit_id` / `user_id` / `home_region` / fencing-epoch metadata, plus a snapshot cursor and `complete_through` watermark. The scan starts from a last-complete checkpoint durably stored on the standby, includes an overlap, deduplicates by event ID and idempotency key, and advances only after the provider watermark covers the scan end and reconciliation finishes. An empty but incomplete scan is not proof of no authorization. If the PSP cannot provide this contract, keep regional admissions paused until a cross-region-durable pre-PSP attempt journal is deployed. See `docs/contracts/psp-ledger-discovery.md` for the interface and tests.
- **PSP webhooks:** Async authorization, capture and 3DS outcomes enter through the authenticated webhook ingress, which verifies signature/timestamp and deduplicates event IDs before appending events to the log. Polling by the same idempotency key remains the fallback for missing or late callbacks. The architecture supports this route; the prototype may implement polling first.
- **DLQ and reconciliation:** Events that exhaust bounded retries enter the DLQ. The reconciler monitors and triages them; replay is operator-approved, audited and performed only after remediation. Reconciliation compares Redis, PostgreSQL and PSP ledger, detects duplicate ownership, orphan authorizations, stuck `PAYING` holds and unit-conservation drift. Automated fixes touch only records older than a safety threshold and in terminally safe states.
- **Hold reaping:** Expired `HELD` holds are returned to availability and the release is appended to the Redis outbox atomically. `PAYING` holds are never timer-released; the reaper repeatedly emits `HoldPayOverdue` to the Redis outbox, then the relay publishes it to Kafka for WRK/REC resolution against DB and PSP truth.
- **Analytics:** The analytics store consumes lifecycle events asynchronously from the event log and has no dependency in the checkout path.
- **Multi-AZ failover:** Gateway, reservation and webhook ingress replicas run statelessly in both AZs. Admission is leased per item, relays per Redis stream, reapers per shard, workers per Kafka partition, capture tasks per payment/task and reconciliation per job. A takeover requires a higher fencing epoch; no worker role is pinned to AZ a.
- **Multi-region:** One home region is the single writer for an item. Other regions serve edge/waiting-room and read traffic; writes are forwarded to the home-region gateway with a fencing epoch. The standby region is a separate PostgreSQL synchronous standby. Only the step-13 confirmation transaction uses `synchronous_commit=on` and waits for remote WAL flush; the step-11 intent transaction uses `synchronous_commit=local` and is locally durable but not cross-region durable. Primary + one remote standby are both required (2-of-2 synchronous primary/standby replication), not a majority consensus quorum. If the WAN/standby is unavailable, confirmation commits and new admission-token issuance pause; existing `PAYING` holds remain locked and the reaper emits `HoldPayOverdue`, never releasing them on a timer. On region loss after PSP authorization but before the step-13 ACK, the order ID itself may be lost with the local-only intent. REC therefore first fences the old writer and establishes a higher epoch, then discovers unknown IDs by scanning the PSP authorization ledger over a bounded time window, using a stable paginated snapshot and filtering returned metadata by `home_region`/epoch. The scan starts from a standby-durable `complete_through` checkpoint with an overlap and ends after the failover cutoff plus provider settlement grace; pages are deduplicated by PSP event ID and idempotency key. REC requires the provider completeness watermark to cover the window end, then performs individual key lookups for discovered/standby-known IDs, verifies any durable step-13 confirmation on the promoted standby, reconstructs idempotent recovery records, and voids authorizations without proof of durable confirmation. The new checkpoint is durably stored and admissions reopen only after complete discovery and reconciliation. If the PSP cannot provide complete ledger discovery and metadata retention, failover stays closed until an independently cross-region-durable pre-PSP attempt journal is available. Unconfirmed local intents are not RPO-0 records. Event-log replication may be asynchronous, but failover requires fencing, WAL recovery, rebuild/reconciliation and PSP-ledger checks before admissions reopen.
- **Observability:** Critical services export metrics, traces and structured logs to OpenTelemetry/Prometheus. Telemetry is non-critical and never gates reserve, checkout or payment resolution.

## Implementation boundary

The current Go starter implements the in-process inventory state machine represented by steps 6–7 plus expiry/confirmation transitions. `Router` now implements and tests the specific-seat/any-unit shard-selection policy, immutable per-hold claim semantics through a local memory repository, and the no-remap-on-drain rule. The Redis `HSETNX` claim adapter and Redis Cluster scripts remain integration work; PostgreSQL synchronous primary/standby replication, the PSP webhook route, distributed workers, versioned KV projection and the DLQ must not be described as implemented until their integration tests pass.
