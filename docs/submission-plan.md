# Spike-Resilient Flash Sale & Ticketing Platform — Submission Plan

**Target outcome:** Deliver the complete assignment package — six proposal sections, ADRs, HLD source + PNG/SVG/PDF, walkthrough, and a runnable full-pipeline Go prototype. Host-side unit/race/static checks and both deterministic and HTTP-level in-memory end-to-end demos are executable locally. Docker-backed Redis/PostgreSQL/Redpanda integration, production-scale load, and true multi-region replication/fencing remain separate acceptance gates and are not represented as completed evidence.

**Architecture (one paragraph):** Collapse demand to supply as early as possible. Up to 10M users wait at the edge; the waiting room serves roughly 500K jittered polls/s from a one-second cached watermark without a per-poll origin call. Admission has two independent dimensions: inventory availability (`OPEN`, `TEMPORARILY_UNAVAILABLE`, terminal `SOLD_OUT`) and an `ACTIVE`/`PAUSED` gate. `PAUSED` preserves queue position and issues no admission token; stale/missing standby ACK, open PSP breaker/capacity exhaustion, unknown stock or lost control plane pauses new admissions but is not `SOLD_OUT`. The origin sees only admitted traffic. Inventory is 50K concrete **unit tokens** in Redis Cluster. Specific-seat routing is `hash(unit_id) % S`; any-unit routing walks from `hash(user_id) % S`. An immutable per-hold `hold-claim:{base64url(hold_id)}` claim uses `HSETNX`; the claim is separate from same-slot per-shard Lua reservation keys. A bound shard that drains returns `SOLD_OUT` for that hold ID and is never remapped. `RELEASED`, `FORFEITED` and `CONFIRMED` hold records are terminal tombstones: reserve replay rejects `RELEASED` and `FORFEITED`, and returns the existing `CONFIRMED` hold without allocating. Claim keys have no TTL while `HELD`/`PAYING`; after a terminal transition the repository applies a configured tombstone TTL longer than every accepted credential/retry/consumer/PSP/webhook/recovery replay window, while the shard-side terminal record is retained at least as long. Expired admission credentials are rejected before reserve. The reservation Lua script moves one unit into a TTL `HELD` hold and appends its outbox event atomically; checkout changes `HELD → PAYING` and returns 202. A Redis Streams relay publishes to a 12-partition Kafka API log keyed by `order_id`, then ACKs only after broker ACK. Workers write a local-WAL `PENDING_PAYMENT + INTENT` before PSP authorization. PSP calls include `order_id` idempotency and item/unit/user/home-region/fencing-epoch metadata. Customer-visible `CONFIRMED` waits for PostgreSQL synchronous primary + one remote standby WAL-flush acknowledgement (`synchronous_commit=on`, 2-of-2, not a majority quorum); step-11 intent is local-only (`synchronous_commit=local`). Standby ACK loss pauses confirmation commits and new admissions; `PAYING` holds are never timer-released. If region loss also erases the order ID, REC discovers unknown authorizations through a stable, paginated PSP ledger scan with a `complete_through` watermark and a standby-durable scan checkpoint, then verifies, reconstructs or voids before reopening. A separate capture sweeper performs deferred idempotent capture. PostgreSQL remains the final oversell and payment-state authority.

**Tech stack (prototype):** Go 1.23 module/toolchain baseline used by the checked-in prototype (stdlib `net/http` and a small libpq/RESP/Redpanda HTTP adapter layer), Redis 7.4+ (Lua + Streams + hostname-aware Cluster endpoints), Redpanda (Kafka API), PostgreSQL 16, k6, Mermaid as the editable HLD notation, and the checked-in Python/CairoSVG renderer for SVG/PNG/PDF exports. Redis, PostgreSQL, Redpanda and application services run through Docker Compose once Task 1 is implemented; the current HLD renderer runs with `python3 scripts/render_hld.py` after installing CairoSVG. Reference production mapping is AWS (CloudFront/edge worker, MemoryDB, MSK, self-managed PostgreSQL 16 on EC2 with synchronous cross-region remote WAL-flush replication, DynamoDB, EKS + KEDA), stated as an assumption with vendor-neutral notes. Aurora Global Database is explicitly not used for the synchronous RPO 0 confirmed-order path because its cross-region replication is asynchronous.

## Approach, and what it was chosen over

| **Approach**                                                                                                         | **Verdict**                                                                                                                                                                                                             |
| :------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. DB-centric**— bigger Postgres, row locks / `SKIP LOCKED`, more replicas                                         | Rejected as the primary design. Strongly consistent and simple, but every request holds a connection; this is the architecture that already failed. Kept only as the final guard (unique index).                        |
| **B. Edge collapse + unit-token holds + async order log + DB uniqueness guard**                                      | **Chosen.** Write volume is bounded by inventory (50K), not demand (10M).                                                                                                                                               |
| **C. Lottery / batch allocation**(inversion: collect entries for N minutes, allocate offline, invite winners to pay) | Not the default — changes the product and removes seat choice — but recorded in the trade-offs doc as a v2 mode for the hottest drops, since it removes the write spike entirely and is the strongest anti-bot posture. |

## Decision ledger (docs, ADRs and code must all agree with this)

| **Topic**            | **Decision**                                                                                                                                                                                                                                                                                                                        |
| :------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where 500K rps goes  | 10M users × ~20 s jittered, server-controlled poll interval ≈ 500K edge polls/s, answered from a 1 s cached admission watermark. These are edge polls, not origin requests; no origin call per poll. |
| Admission rate       | `min(0.7 × PSP limit ÷ hold→pay conversion, reservation capacity, available inventory)`. Assumed PSP limit 2,000 calls/s and 80% hold→pay conversion → 1,400 auth/s → ~1,750 admitted users/s. Closed-loop: slow/pause when breaker opens, p99 degrades, stock is unknown, control plane is lost, or the remote standby ACK is stale/missing. |
| Admission state      | Inventory state (`OPEN`, `TEMPORARILY_UNAVAILABLE`, `SOLD_OUT`) is separate from admission gate (`ACTIVE`, `PAUSED`). `PAUSED` preserves queue position and issues no token; it is never terminal `SOLD_OUT`. Pause on unknown stock, PSP breaker/capacity loss, lost CTRL, or stale/missing remote-standby WAL-ACK health. Existing `PAYING` holds remain locked and emit `HoldPayOverdue`; browse remains available from CDN. |
| Queue fairness       | Arrivals before T0 are shuffled into a random order (no reward for refresh-spamming or bot head starts); arrivals after T0 are FIFO. Position is approximate by design.                                                                                                                                                             |
| Edge tokens          | Signed queue token (position) → signed short-lived admission token. Origin verifies offline; no session store on the hot path.                                                                                                                                                                                                      |
| Inventory model      | Each unit/seat is a token in a per-shard Redis set. `reserve` = atomic Lua: pop (or `SREM` a specific seat) → hold record → expiry index → outbox event. Deadlines use Redis server `TIME`, one clock.                                                                                                                              |
| Hot key              | Primary defence is admission control (≤5K writes/s reaches inventory). Secondary: S inventory sub-buckets with hash tags `{item:shard}` spread one item over cluster slots. Specific seat → `hash(unit_id) % S`; any-unit → start at `hash(user_id) % S` and walk deterministically. The immutable claim is stored under a per-hold key `hold-claim:{base64url(hold_id)}` using `HSETNX`, not a single per-item key; claim keys therefore distribute across Redis Cluster slots. Claim and reserve are separate operations because the claim key and inventory-shard keys occupy different slots. If the chosen shard drains after the stock probe but before reserve, reserve returns `SOLD_OUT`; the claim never moves and this attempt may be falsely sold out rather than risking a second allocation. |
| Holds                | `HELD` (TTL 5 min) → `PAYING` (locked at checkout) → `CONFIRMED`, `RELEASED` or `FORFEITED`. All terminal states are tombstones. Reserve replay rejects `RELEASED` and `FORFEITED`; `CONFIRMED` replay returns the same hold without allocating. `Release` returns a unit only after expiry of `HELD` or a definitive PSP decline/void. `Forfeit` never returns a unit and requires durable payment evidence: `HELD` requires `NOT_ATTEMPTED`; `PAYING` permits `NOT_ATTEMPTED` only for a persisted unique-guard loser that short-circuited before PSP, or a definitive persisted PSP `DECLINED`/`VOIDED` result. `AUTHORIZED`, `UNKNOWN` or ambiguous attempts cannot be forfeited. Claim TTL is applied only after terminal state and exceeds every accepted replay/credential/PSP/recovery window; no TTL while `HELD`/`PAYING`. The reaper releases only expired `HELD`, never `PAYING`, and emits `HoldPayOverdue`. |
| Failure direction    | Network/timeouts and ambiguous payment outcomes prefer *temporary under-selling* (stranded or `PAYING` holds), never over-selling. A unique-guard loser is a distinct correctness action: `FORFEIT` permanently keeps that unit unavailable under the losing hold; it is not returned to sale unless authoritative reconciliation later proves that doing so is safe. |
| Final oversell guard | `UNIQUE (item_id, unit_id) WHERE status <> 'CANCELLED'` in the relational DB. Redis is a fast admission filter, not the system of record.                                                                                                                                                                                           |
| Sync vs async        | Sync (p99 < 500 ms SLO): reserve and checkout-accept (returns 202 + status URL). Async: order intent is locally WAL-flushed (`synchronous_commit=local`), followed by PSP authorization; expose `CONFIRMED` only after the step-13 PostgreSQL primary + remote standby synchronous WAL-flush acknowledgement (`synchronous_commit=on`, 2-of-2; not a majority quorum). Stale/lost standby ACK pauses new admission-token issuance. Capture is owned by a separate deferred sweeper. Separate SLO: 95% terminal < 5 s, 99% < 15 s. |
| Log                  | Kafka API (MSK in prod, Redpanda in prototype). Partition key `order_id` — per-order ordering, even spread, no hot partition for a hot item. At-least-once delivery + idempotent consumers = exactly-once *effects*.                                                                                                                |
| Redis → log          | Each Lua script `XADD`s to a per-shard Redis Stream in the same atomic step (outbox); a relay ships it to the log and `XACK`s after produce.                                                                                                                                                                                        |
| Payments             | Order + payment intent are locally WAL-flushed before the PSP call (`synchronous_commit=local`); the intent is intermediate and not yet cross-region durable. Authorize with `Idempotency-Key = order_id` and include `order_id`, item/unit/user/home-region/fencing-epoch PSP metadata; timeout means `UNKNOWN` and is resolved by query/retry/void using the same known key. Confirm only after definitive authorization and PostgreSQL synchronous remote-standby WAL-flush acknowledgement (`synchronous_commit=on`, primary + one remote standby, 2-of-2; not a majority quorum). |
| PSP ledger discovery | Known order ID: `GET /charges/{idempotency_key}`. Unknown order ID after regional loss: stable paginated authorization-ledger scan over a bounded time window. Each page returns snapshot/cursor, event and charge IDs, idempotency key/order ID, authorization status/time, full request metadata and provider `complete_through`; REC filters `home_region`/epoch locally even if provider filtering is optional. An empty page is not proof of absence until the completeness watermark covers the scan end. |
| PSP recovery checkpoint | REC maintains a periodic scan checkpoint during normal operation. It stores home region, snapshot ID, scan bounds, `complete_through` and epoch in PostgreSQL with `synchronous_commit=on` only after all pages and reconciliation complete. Failover scans start at checkpoint minus overlap and end at failover detection plus configured PSP settlement grace; dedupe by event ID and idempotency key. If metadata retention, stable pagination or completeness cannot be guaranteed, regional writes remain paused until a cross-region-durable pre-PSP attempt journal exists. |
| PSP void/tombstone capability | Prefer a PSP with definitive void-by-idempotency-key tombstoning: after confirmed void, late authorization for that key is refused. If a PSP cannot guarantee this, an `UNKNOWN` authorization remains `PAYING` and is not cancelled/released until a definitive webhook/status/ledger result or provider-guaranteed finality boundary proves no late authorization can land. Idempotency-window expiry alone is not proof of finality. |
| PSP protection       | Dedicated worker pool (bulkhead) sized to the PSP quota, token bucket below quota, 2 s timeout, circuit breaker. Breaker open → pause/reduce new admissions; never release `PAYING` holds on timer evidence. Existing payment outcomes continue through query/retry/void resolution. Timer-freeze/hold-extension behaviour is a documented design option, not claimed as implemented in the prototype.                                                                                              |
| Worker HA            | APP replicas are stateless in both AZs. A leader-elected regional lease-renewal controller (one active renewer per home-region writer lease, with HA replacements across AZs) renews the logical regional writer lease; `region_leases.owner_id` is the active region/cluster writer identity shared by worker replicas, never a pod hostname. ADM uses per-item leases, RLY per-stream leases, REAP per-shard leases, WRK Kafka partition ownership, CAP per-payment/task ownership, and REC a periodic lease. A higher fencing epoch is required for takeover; no worker role is pinned to AZ a. |
| Regional lease renewal | A leader-elected lease-renewal controller for the active logical regional writer renews before `lease_expires_at` (configurable duration; default target is renewal at roughly one-third of the lease duration). It uses a conditional `UPDATE` matching `home_region`, logical `owner_id`, current `epoch` and an unexpired lease. Zero rows, DB uncertainty or renewal deadline miss means self-fence immediately: stop new writes, pause admissions and confirmation, and do not assume the lease remains owned. Renewal runs independently from order workers; no DB transaction/lock is held during PSP calls. |
| Webhooks and DLQ      | Authenticated PSP webhook ingress validates signature/timestamp/replay and deduplicates event IDs, then appends events to the log; it bypasses the waiting room. Consumers use bounded retries → requeue → DLQ; offsets advance only after a durable successful outcome, durable requeue, or durable DLQ + `UNKNOWN`; reconciler triages DLQ and replay is controlled/audited after remediation. |
| Data placement       | Redis inventory keyspace: units, holds, deadlines and per-shard Streams outbox. Separate replicated HA control-plane keyspace/partition: per-item watermark, inventory state, ACTIVE/PAUSED gate, stock summary, PSP breaker/effective capacity and timestamped standby-ACK health. PostgreSQL: authoritative orders/payments, durable idempotency, `region_leases` and fencing epochs, unit uniqueness, inventory disposition, and standby-durable PSP ledger-scan checkpoint. KV: versioned status read model/catalog, never payment authority. Log: lifecycle events + DLQ; analytics: columnar store. |
| Caching              | CDN: static + catalog (minutes), availability (1 s + stale-while-revalidate, bucketed "many / few / sold out"). Local: in-process 1 s cache with singleflight coalescing. Redis only for the authoritative path.                                                                                                                    |
| Scaling              | Scheduled: pre-warm everything at T-30 min (pods, pools, LB, caches, inventory load). Unscheduled: always-armed edge queue engages in < 10 s on origin RPS/latency/error thresholds, then autoscale on leading signals (RPS per pod, in-flight concurrency, log lag *age*, waiting-room size). CPU lags 2–5 min behind a 30 s ramp. |
| Shed order           | Bots/unauthenticated → non-essential (recs, beacons, search) → freshness (serve stale) → new admissions (slow the queue). Never shed: checkout for users holding stock, PSP webhooks, confirm/release.                                                                                                                              |
| Retries              | Clients: exponential backoff + full jitter, retry budget, honour `Retry-After`; poll cadence is server-controlled. Internal: retry at one layer only, propagated deadlines, retry budgets, no retry without an idempotency key.                                                                                                     |
| Multi-region         | Each item has a **home region** that is the single writer for inventory and orders. Other regions serve edge, waiting room and reads, and forward writes with a fencing epoch. Step-11 intent is local-WAL only; customer-visible confirmation waits for PostgreSQL primary + one remote standby synchronous WAL-flush acknowledgement (2-of-2, not majority quorum). Stale/lost standby ACK pauses new admissions and confirmation commits. Because this local-only intent and the async Kafka replica can both be lost, REC discovers unknown order IDs by paginated PSP ledger scan, uses a standby-durable `complete_through` checkpoint, overlap and settlement grace, verifies durable step-13 confirmations, voids unconfirmed authorizations, and reconciles before reopening. This failover procedure assumes the old home region is confirmed unreachable or independently fenced before standby promotion. A per-region `region_leases` row is not a global fence during a split-brain partition where both regions can still accept writes; consensus-backed or external fencing authority is required for that stronger guarantee and is outside this prototype's scope. If the PSP cannot meet the discovery contract, failover stays closed until a cross-region-durable pre-PSP journal is deployed. |
| Split-brain boundary | The per-region `region_leases` row and its epoch fence stale workers only within the authoritative promoted PostgreSQL history; they do not globally fence two independently writable regional primaries during a network partition. Promotion is allowed only after the old primary is confirmed unreachable or infrastructure-fenced. True partition-safe automatic failover needs an external/consensus fencing authority and is not implemented or tested in this prototype. |
| RPO / RTO            | RPO 0 applies only to acknowledged step-13 confirmations whose remote standby WAL-flush ACK returned. Step-11 local-only intents are not covered. Pre-ACK region loss requires a complete PSP-ledger discovery scan and reconciliation; any authorization without proof of a durable `CONFIRMED` commit is voided, and unresolved outcomes keep admissions paused. Confirmation commits and new admissions pause if standby/WAN ACK health is unavailable. RTO targets: AZ <60s automatic; region <15min for sale path; browse stays available from CDN stale data. |
| Build vs buy         | Buy: waiting room, bot management, CDN/WAF, managed log and DBs. Build: reservation core, payment orchestration, reconciliation — the parts where the correctness guarantees live.                                                                                                                                                  |

## HLD contract: numbered flow and supporting paths

The plan is subordinate to the reviewed HLD source at `docs/diagrams/hld.mmd` and its companion `docs/architecture/hld-walkthrough.md`. The primary flow is exactly 15 cards, read serpentine: row 1 left-to-right, row 2 right-to-left, row 3 left-to-right. Keep the component names and order synchronized across the diagram, walkthrough, plan and implementation tasks.

| HLD card | Component | Plan-level contract |
|---:|---|---|
| 1 | Browse / availability | CDN serves catalog/static data for minutes and bucketed availability for about 1 s + stale-while-revalidate; cache never allocates inventory. |
| 2 | Join / poll waiting room | Up to 10M waiters; approximately 500K edge polls/s under the 20 s jittered-poll assumption; polls use cached watermark and do not call origin. `PAUSED` preserves position and issues no admission token. |
| 3 | Admission control | Publishes 1 s watermark plus `ACTIVE`/`PAUSED` gate using stock, PSP capacity/breaker, control-plane health and timestamped remote-standby ACK health. Inventory state is separately `OPEN`, `TEMPORARILY_UNAVAILABLE` or terminal `SOLD_OUT`. |
| 4 | Signed admission token | Short-lived signed token verified offline at gateway; status and authenticated PSP webhook paths have separate authorization. |
| 5 | API gateway | Admitted reserve/checkout traffic only; priority shedding; assumed safe admission around 1,750/s; reservation p99 SLO <500 ms. |
| 6 | Reservation router | Specific seat: `hash(unit_id) % S`; any unit: deterministic walk from `hash(user_id) % S`; immutable per-hold `hold-claim:{base64url(hold_id)}` claim via `HSETNX`; no remap after claim. |
| 7 | Redis atomic hold | Same-slot Lua atomically moves unit to `HELD`, records deadline using Redis `TIME`, appends outbox event; checkout moves `HELD → PAYING`, returns 202 + status URL. Reaper never timer-releases `PAYING`. |
| 8 | Outbox relay | One lease owner per Redis stream; pending-entry replay after restart; publish to Kafka and `XACK` only after broker ACK. |
| 9 | Kafka API event log | 12 partitions keyed by `order_id`; per-order ordering; at-least-once; bounded retry → requeue → DLQ; commit offset only after durable success, durable requeue, or durable DLQ + `UNKNOWN`. |
| 10 | Order workers | Create local-WAL order/payment intent before PSP call; dedicated bulkhead and per-PSP-call token bucket; authorize and confirm only; capture belongs to CAP. |
| 11 | PostgreSQL order intent | Local transaction `PENDING_PAYMENT + INTENT` (`synchronous_commit=local`); partial unique live-unit guard; loser is recorded `CANCELLED`, bypasses PSP, forfeits hold pending reconciliation. |
| 12 | PSP authorize | `Idempotency-Key = order_id`; include order/item/unit/user/home-region/fencing-epoch metadata; timeout is `UNKNOWN`; assumed authorization budget ≤1,400 calls/s. |
| 13 | Cross-region sync ACK | On definitive authorization, CAS `AUTHORIZED + CONFIRMED` with `synchronous_commit=on`; wait for primary + one remote standby WAL flush (2-of-2, not majority quorum). No ACK pauses confirmations and new admissions. |
| 14 | Finalize inventory | Only after remote ACK, mark Redis unit sold and never re-offer; release only after definitive decline/void; unique-guard loser is forfeited pending reconciliation. |
| 15 | Order status read | Versioned KV fast path; miss/stale falls back to PostgreSQL; before order row exists, Redis returns `PAYING`/`PROCESSING`. |

Supporting flows are not extra numbered cards: PSP webhook ingress (signature/timestamp/replay verification + event-ID dedupe), CAP deferred idempotent capture, REAP `HELD` release / `PAYING` `HoldPayOverdue`, DLQ triage, REC three-way reconciliation and regional PSP-ledger discovery, other-region write forwarding with fencing, asynchronous analytics/log replica, and non-critical OTel/Prometheus telemetry.

## HLD-to-plan synchronization checklist

Before accepting a plan change, verify all of the following against `docs/diagrams/hld.mmd`, `docs/architecture/hld-walkthrough.md`, ADR 0002, ADR 0005 and `docs/contracts/psp-ledger-discovery.md`:

- The numbered request path remains 1–15 in serpentine order: 1–5 edge/API; 6 router; 7 Redis hold; 8 outbox relay; 9 Kafka; 10 workers; 11 local order intent; 12 PSP authorization; 13 remote synchronous WAL-flush acknowledgement; 14 inventory finalization; 15 order-status read.
- `PAUSED` is an admission gate, not an inventory state or terminal `SOLD_OUT`; it preserves queue position and issues no token. A stale/missing standby ACK pauses new admissions; existing `PAYING` holds remain locked and emit `HoldPayOverdue`.
- The immutable per-hold claim uses `hold-claim:{base64url(hold_id)}` and `HSETNX`; the per-shard Lua transaction touches only keys in one `{item:shard}` slot. A bound shard is never remapped after drain or an ambiguous result.
- The outbox relay publishes then acknowledges only after broker ACK; Kafka offsets move only after a durable outcome, durable requeue, or durable DLQ plus `UNKNOWN` state.
- Step 11 is local-WAL `PENDING_PAYMENT + INTENT`; step 13 is the 2-of-2 PostgreSQL primary + remote standby WAL-flush commit. RPO 0 applies only to acknowledged `CONFIRMED` orders; this is not a majority quorum and does not map to Aurora Global Database.
- Known PSP keys use per-key lookup. Unknown keys after regional loss require the stable paginated ledger scan, metadata, provider `complete_through`, standby-durable checkpoint, overlap, settlement grace, idempotent dedupe, and fail-closed reconciliation gate.
- CAP remains deferred from the order-worker hot path; REC owns reconciliation and regional recovery; versioned KV is a read model, never payment authority.

```
type HoldState string
const (
  HoldHeld HoldState = "HELD"
  HoldPaying HoldState = "PAYING"
  HoldConfirmed HoldState = "CONFIRMED"
  HoldReleased HoldState = "RELEASED"
  HoldForfeited HoldState = "FORFEITED"
)

type Hold struct { ID, Item, Unit, User string; State HoldState; Deadline time.Time }

type ForfeitProof string
const (
  ForfeitProofNotAttempted ForfeitProof = "NOT_ATTEMPTED"
  ForfeitProofPSPDeclined  ForfeitProof = "PSP_DECLINED"
  ForfeitProofPSPVoided    ForfeitProof = "PSP_VOIDED"
)
// ValidateForfeitProof allows HELD only with NOT_ATTEMPTED; PAYING accepts
// NOT_ATTEMPTED only for a persisted unique-guard loser that never called PSP,
// or a definitive persisted PSP_DECLINED / PSP_VOIDED result. AUTHORIZED,
// UNKNOWN and ambiguous outcomes return ErrUnsafeForfeit. An already-FORFEITED
// hold is an idempotent no-op and needs no new proof.

type Store interface {
  Seed(ctx context.Context, item string, units []string) error
  Reserve(ctx context.Context, item, holdID, user, unit string) (Hold, error) // rejects RELEASED/FORFEITED; confirmed replay returns same hold
  LockForPayment(ctx context.Context, item, holdID string) (Hold, error)
  Confirm(ctx context.Context, item, holdID string) error   // idempotent terminal SOLD
  Release(ctx context.Context, item, holdID string) error  // idempotent; returns unit only after safe release decision
  Forfeit(ctx context.Context, item, holdID string, proof ForfeitProof) error // idempotent; validates hold state + durable payment proof
  Reap(ctx context.Context, item string, shard, limit int) (released, overdue int, err error)
}
```

Per-shard reserve script (the other five scripts—checkout, confirm, release, forfeit and reap—follow the same shape: check state, mutate, and `XADD`). **Precondition:** the router has already resolved the immutable per-hold claim and selected this exact shard. Every key passed to this Lua script belongs to the selected `{item:shard}` hash slot; the script never accesses the per-hold claim key because that key is in a different Redis Cluster slot:

```
-- KEYS: avail, holds, exp, events (all same {item:shard} slot)
-- ARGV: hold_id, user_id, ttl_ms, requested_unit_id ("" = any)
-- The immutable hold-claim:{base64url(hold_id)} was resolved by the router first.
local existing = redis.call('HGET', KEYS[2], ARGV[1])
if existing then
  local prior = cjson.decode(existing)
  if prior.user ~= ARGV[2] or prior.requested_unit ~= ARGV[4] then
    return {'REPLAY_MISMATCH'}
  end
  if prior.state == 'RELEASED' then
    return {'RELEASED'} -- terminal hold_id: never allocate again
  end
  if prior.state == 'FORFEITED' then
    return {'FORFEITED'} -- terminal hold_id: never allocate again
  end
  if prior.state == 'HELD' or prior.state == 'PAYING' or prior.state == 'CONFIRMED' then
    return {'OK', existing} -- active/confirmed replay; never allocate again
  end
  return {'INVALID_STATE'}
end
local unit
if ARGV[4] ~= '' then
  if redis.call('SREM', KEYS[1], ARGV[4]) == 0 then return {'TAKEN'} end
  unit = ARGV[4]
else
  unit = redis.call('SPOP', KEYS[1])
  if not unit then return {'SOLD_OUT'} end
end
local t = redis.call('TIME')
local deadline = t[1] * 1000 + math.floor(t[2] / 1000) + tonumber(ARGV[3])
local rec = cjson.encode({unit = unit, user = ARGV[2], requested_unit = ARGV[4], state = 'HELD', deadline = deadline})
redis.call('HSET', KEYS[2], ARGV[1], rec)
redis.call('ZADD', KEYS[3], deadline, ARGV[1])
redis.call('XADD', KEYS[4], '*', 'type', 'HoldCreated', 'hold_id', ARGV[1], 'unit', unit, 'user', ARGV[2], 'requested_unit', ARGV[4])
return {'OK', rec}
```

`release.lua` retains a `RELEASED` tombstone in the per-shard holds hash and never deletes it on the hot path. It may transition an expired `HELD` hold, or a `PAYING` hold only after the caller has established a definitive PSP decline/void; it returns the unit to availability exactly once. `confirm.lua` retains `CONFIRMED` and marks the unit sold/unavailable. `forfeit.lua` accepts `ARGV` proof (`NOT_ATTEMPTED`, `PSP_DECLINED` or `PSP_VOIDED`) supplied only by the trusted payment orchestrator after checking the durable PostgreSQL payment state and, where applicable, a definitive PSP result. Forfeit is a permanent quarantine, not the ordinary payment-decline path; a normal definitive decline/void uses `Release` unless a separate invariant requires permanent retirement. It validates the proof/state combination before any mutation; unknown/invalid proof returns `UNSAFE_FORFEIT` and leaves the hold/deadline/available set unchanged. `HELD` accepts only `NOT_ATTEMPTED`. `PAYING` accepts `NOT_ATTEMPTED` only for a persisted unique-index loser whose payment row proves no PSP attempt occurred, or `PSP_DECLINED`/`PSP_VOIDED` after the definitive result is persisted. `AUTHORIZED`, `UNKNOWN`, missing proof and ambiguous outcomes are rejected; REC must resolve/void them before calling Forfeit. The script then transitions the eligible hold to terminal `FORFEITED`, removes its deadline, records disposition, appends `HoldForfeited`, and never adds its unit to the available set; repeated forfeiture is idempotent. It rejects transitions from `RELEASED` or `CONFIRMED`; an already-`FORFEITED` record returns idempotent success. The Lua proof value is a trusted caller assertion, not independent PSP verification; the worker must derive it from the fenced DB/PSP decision before invoking the script. A `FORFEITED` hold ID is rejected by reserve replay with `ErrHoldForfeited`. `RELEASED`, `CONFIRMED` and `FORFEITED` are terminal states. `ExpireAfterTerminal` applies only after the respective terminal hold record is durably written; it must include `Forfeit` in the same lifecycle hook as `Confirm` and `Release`. Terminal hold hash fields are removed only by item-scoped cleanup after the corresponding claim-retention window and admission-token/replay windows have expired. The claim key and terminal record must not be cleaned up while a valid reserve credential or accepted replay can still refer to the hold. `FORFEITED` uses the same terminal-only claim TTL and tombstone-retention rules as `RELEASED` and `CONFIRMED`. A failed claim-key EXPIRE leaves the key present and safe; it must not trigger early tombstone deletion.

The worker maps durable payment rows to proof as follows: `NOT_ATTEMPTED` only when the unique-index loser was committed before any PSP call; `PSP_DECLINED` or `PSP_VOIDED` only after the definitive PSP result is persisted in a fenced transaction. A normal decline uses `Release`; the declined/voided proofs are accepted by `Forfeit` only when a separate safety/integrity decision requires the unit to remain permanently quarantined. Never synthesize proof from a timeout, missing row, idempotency-window expiry or best-effort lookup. ### Task 3 — Tokens, admission control and waiting room (R2, R3, R8)

- Admission gate: `ACTIVE` or `PAUSED`.

```sql
);
CREATE UNIQUE INDEX orders_one_owner_per_unit
  ON orders (item_id, unit_id) WHERE status <> 'CANCELLED';

CREATE TABLE payments (
  order_id uuid PRIMARY KEY REFERENCES orders,
  status text NOT NULL CHECK (status IN ('NOT_ATTEMPTED','INTENT','AUTHORIZED','CAPTURED','FAILED','VOIDED','UNKNOWN')),
  psp_charge_id text,
  amount_minor bigint NOT NULL,
  attempts int NOT NULL DEFAULT 0,
  last_attempt_fencing_epoch bigint,
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

The `region_leases.owner_id` is a stable logical writer identity such as `us-east-1-primary`, shared by all worker replicas in that active home-region writer group; it is not an individual worker hostname. A leader-elected `lease-manager` controller (one active renewer per home-region writer lease, with replacement instances across AZs) owns renewal. It renews at `lease_expires_at - renewal_lead_time` (configurable; target approximately one-third of the lease duration), independently of order-worker goroutines. Renewal is a short conditional update: `UPDATE region_leases SET lease_expires_at = clock_timestamp() + $duration, updated_at = clock_timestamp() WHERE home_region = $home_region AND owner_id = $logical_owner_id AND epoch = $current_epoch AND lease_expires_at > clock_timestamp() RETURNING lease_expires_at;`. Exactly one row must be returned. Zero rows, database uncertainty past the safety margin, or a missed renewal deadline means the controller self-fences: stop issuing/accepting new writes, publish lease-unhealthy to CTRL, pause admissions/confirmation and require lease ownership to be re-established; never revive an expired lease with the renewal query. Renewal takes no lock across PSP calls, and no worker transaction is held during PSP I/O. The lease-manager has its own leader-election/health signal; worker replicas do not each race to renew the regional writer lease. A replacement lease-manager may continue renewal with the same logical `owner_id` and epoch while the regional writer remains authoritative; only an actual region takeover changes `owner_id` and increments epoch.

`orders.version` is the aggregate version for both order and payment transitions. Increment it exactly once for each committed aggregate-state transition; when order and payment rows change together in one atomic transaction, increment once for that transaction (not once per row). Every KV event carries `(order_id, version, order_status, payment_status, inventory_disposition)` and the projection accepts only a strictly newer version. A DB commit is authoritative even if its KV projection fails; the event is replayed/rebuilt from PostgreSQL and must never be acknowledged as successfully projected until repair is durably scheduled. `orders.fencing_epoch` records the epoch of the latest accepted mutation; `payments.last_attempt_fencing_epoch` records the epoch attached to the latest PSP attempt. Every worker write transaction acquires locks in one order: first lock the matching `region_leases` row with `SELECT ... FOR SHARE`, verify `owner_id`, lease validity and that the supplied epoch equals the current epoch, then lock/update order and payment rows and perform the CAS. Hold the lease share lock until that short transaction commits. Takeover uses `BEGIN; SELECT ... FROM region_leases WHERE home_region=$1 FOR UPDATE; UPDATE region_leases SET owner_id=$2, epoch=epoch+1, lease_expires_at=$3, updated_at=now() WHERE home_region=$1; COMMIT;`. `FOR UPDATE` waits for current worker `FOR SHARE` transactions to finish; after takeover commits, new/stale worker transactions must fail the epoch check. Never acquire order/payment locks before the lease row. Never hold a DB transaction open over a PSP network call: validate the lease in a short transaction before the call, include the epoch in PSP metadata, then acquire/validate the lease again in a new short transaction before persisting the result. A PSP call racing with fencing is resolved by regional ledger reconciliation, not by allowing an old-epoch write. This row-lock/epoch protocol protects transactions against stale epochs in the authoritative PostgreSQL history; it is not a global fence if a network partition leaves two independently writable regional primaries. Promote the standby only after the old primary is confirmed unreachable or separately fenced by infrastructure. Split-brain partition handling with both regions independently reachable requires an external/consensus fencing authority and is explicitly outside this prototype; tests cover region loss/controlled promotion, not dual-primary split brain.


Worker steps for `CheckoutRequested` (capture is a separate sweeper; every operation is idempotent; source offset is committed only after durable success, durable requeue, or durable DLQ + `UNKNOWN`):

1. Begin a short DB transaction: lock/validate the current `region_leases` epoch; insert order `PENDING_PAYMENT` + payment `INTENT` with `orders.version=1` and the current `fencing_epoch`. Use `ON CONFLICT (order_id) DO NOTHING` only for an order-ID replay, then read back and verify immutable `item_id`, `unit_id`, `user_id` and `home_region` against the stored row. After the DB commit, publish the versioned `PENDING_PAYMENT`/`INTENT` projection; a failed KV write is repairable from PostgreSQL and must not be interpreted as payment failure. The status API falls back to authoritative PostgreSQL or pre-row Redis `PAYING` state when KV is missing/stale. If the partial unique live-unit index rejects a different order ID, roll back; in a fresh fenced transaction persist the loser as `CANCELLED`, create its payment row as `NOT_ATTEMPTED` (no PSP operation occurred), set `inventory_disposition='FORFEIT'`, assign the initial aggregate version (or increment it if repairing an existing row), and increment `oversell_guard_trips`. Commit this terminal record before acknowledging; step 2 applies `Store.Forfeit(..., ForfeitProofNotAttempted)` idempotently because the payment row proves no PSP call occurred, then NEVER calls PSP.
2. Load order + payment and process absorbing states before any PSP call:
   - `order.status == 'CANCELLED'`: apply persisted `inventory_disposition` idempotently (`FORFEIT` calls `Store.Forfeit` with proof derived from the durable payment row (`NOT_ATTEMPTED` for unique-guard loser, otherwise persisted definitive `PSP_DECLINED`/`PSP_VOIDED`); `RELEASE` returns it only after definitive decline/void; `SOLD` remains unavailable/confirmed; `NONE` makes no inventory mutation), project `CANCELLED` with current `orders.version`, then acknowledge. NEVER call PSP.
   - `order.status == 'CONFIRMED'`: ensure Redis `Confirm`, project committed `order_status`, `payment_status` and version (including `CAPTURED` if already captured), then acknowledge. NEVER authorize again.
   - `payment.status IN ('AUTHORIZED','CAPTURED')`: skip authorization and resume only missing confirmation/finalization/projection. `CAPTURED` with a non-confirmed order is an invariant violation for REC, not a reason to authorize again.
   - `payment.status IN ('FAILED','VOIDED')`: repair terminal `CANCELLED` state and correct `RELEASE` disposition, project it, and acknowledge. `NOT_ATTEMPTED` is valid only for a cancelled unique-guard loser and is handled by the earlier `order.status == 'CANCELLED'` branch. NEVER authorize again.
   - `payment.status == 'UNKNOWN'`: query the same known idempotency key; do not create a new key or blindly authorize. If lookup returns authorized, persist `AUTHORIZED` through a fenced CAS, increment the aggregate version and continue to step 4; if it returns definitive decline/void, persist terminal `FAILED`/`VOIDED` + `CANCELLED` + `RELEASE` through a fenced CAS, increment the aggregate version and repair projections; if still ambiguous, retain `PAYING`/`UNKNOWN`, perform bounded retry/requeue/DLQ handling, and do not release inventory.
   - `payment.status == 'INTENT'`: continue to step 3 using the same `order_id` key. After an uncertain network result, query first or replay only the identical key under the PSP's documented idempotency contract.
3. Before PSP authorization, validate the current lease/epoch in a short transaction. Call authorize with `Idempotency-Key = order_id`, 2 s timeout, and item/unit/user/home-region/fencing-epoch metadata. The PSP call is outside the DB transaction. Definitive decline → fenced CAS to `FAILED`, `CANCELLED`, `inventory_disposition='RELEASE'`; release only after the definitive decline. Timeout/5xx → persist payment `UNKNOWN` through a fenced CAS, increment aggregate `orders.version`, record `last_attempt_fencing_epoch`, and project the versioned UNKNOWN state; query the same key with jittered backoff. If the DB write itself is unavailable, leave the durable intent untouched and let redelivery/PSP ledger reconciliation discover the attempt. Never release inventory on timeout. 429 → back off and do not advance. A stale epoch discovered after the call cannot commit a DB state change; regional REC discovers the attempt from PSP metadata.
4. After definitive authorization, run a new fenced transaction: lock/validate `region_leases`; CAS payment to `AUTHORIZED` and order to `CONFIRMED`; set `inventory_disposition='SOLD'`; increment aggregate `orders.version` once for this transaction; update `orders.fencing_epoch` and `payments.last_attempt_fencing_epoch`. In production this transaction uses `synchronous_commit=on` and waits for remote standby WAL flush (2-of-2). Step-11 intent uses `synchronous_commit=local` only and is not cross-region durable. A unique/CAS mismatch never transitions `CANCELLED` to `CONFIRMED`.
5. Only after remote ACK (or the explicitly marked local test gate described below), Redis `Confirm` and project `CONFIRMED` to KV using aggregate `orders.version`. Every durable order/payment transition, including `PENDING_PAYMENT`, `UNKNOWN`, `AUTHORIZED` when persisted separately, `CANCELLED`, and `CAPTURED`, is projected with the aggregate order version and both order/payment statuses; KV accepts only newer versions. On projection failure, rebuild from authoritative DB state; never infer payment success from KV.
6. The `capture` role is a separate sweeper: idempotent deferred capture, CAS to `CAPTURED`, increment aggregate `orders.version`, and project that version off the order-worker hot path. The `reconcile` role handles `HoldPayOverdue` from DB then PSP. If the PSP guarantees void-by-key tombstoning, void first and wait for the tombstone result before cancellation/release. If it does not, keep unresolved `UNKNOWN` orders `PAYING` until a definitive webhook/status/ledger result or provider-guaranteed authorization-finality boundary; idempotency-window expiry alone is not sufficient. Tests cover every replay branch (CANCELLED/CONFIRMED/AUTHORIZED/CAPTURED/FAILED/VOIDED/UNKNOWN/INTENT/NOT_ATTEMPTED), assert a CANCELLED or CONFIRMED replay makes zero PSP calls, verify FORFEIT versus RELEASE disposition, worker crash boundaries, stale-epoch write rejection before and after PSP calls, aggregate version increments exactly once per transaction containing an order/payment state transition, monotonic KV projection under reordered/duplicate updates, unique-unit guard, decline release, relay redelivery, capture-sweeper idempotency, DLQ and breaker behaviour. Lease tests additionally cover `TestLeaseRenewal_ExtendsOnlyCurrentOwnerEpoch`, `TestLeaseRenewal_ZeroRowsSelfFences`, `TestLeaseRenewal_ExpiredLeaseCannotBeRevived`, `TestLeaseRenewal_ConcurrentWithTakeover`, `TestLeaseManager_UsesLogicalOwnerAcrossWorkerReplicas`, and `TestOldEpochWriteRejectedAfterTakeover`. The region-loss/controlled-promotion test is in scope; a dual-primary network-partition/split-brain test is explicitly out of scope until an external/consensus fencing authority is added.
